⚖️ LLM Council Report — Nook Loyalty App

Generated 11 May 2026 · 5 Advisors · 5 Peer Reviewers · 1 Chairman
Question brought to the council: Is the Nook QR loyalty PWA truly "elite" and production-ready? What are the real safety and UI/UX concerns that must be addressed before this is something to be proud of publicly?
⚡ The One Thing to Do First

Audit and restrict the Supabase anon key exposure. Right now, the deployed config.js hands anyone who visits the site the key to query all customer records — phone numbers, stamp histories, birthday data. Row-level security policies must be tightened so the anon key cannot return customer PII under any query. If that means temporarily restricting the nook-read Edge Function while you sort it, do that. Everything else on the fix list is real and follows — but you cannot responsibly add more customers to a system that is currently exposing the ones already in it.

📋 Chairman's Verdict
Council Synthesis FINAL

Where the Council Agrees

Every advisor who engaged seriously with the code agrees on three things: the app is not production-ready in its current state. It has a coherent concept, genuine aesthetic ambition, and a working architecture. It is also currently shipping with critical security vulnerabilities and accessibility failures that will cause real harm to real people.

The 9,000-ID space with no collision detection is a trust-destroying bug. When two customers silently share a QR code and one redeems the other's reward, the café owner stands at the counter explaining that someone's loyalty points are gone. That is the moment this app fails in public.

The innerHTML injection on e.note is a genuine XSS vector. It is not theoretical — staff and admin input flows directly into the DOM with no sanitization.

The font sizes are a functional barrier, not an aesthetic statement. 5–8px text with zoom locked via user-scalable=no means real customers cannot use this app. This is inaccessibility with legal exposure attached.

Where the Council Clashes

The Expansionist called the ID collision and font issues "polish problems" while pitching a SaaS pivot. All five peer reviewers identified this as the session's biggest blind spot — dangerous framing that could convince a developer to ship a cracked foundation because the business case sounds exciting.

The real productive disagreement is about severity ranking. The First Principles Thinker correctly reframes: for a neighborhood café, a disgruntled employee exploiting XSS via a crafted note is a more credible threat than an external attacker. Severity should be calibrated to realistic threat actors, not abstract CVE scores.

On SHA-256 vs bcrypt/Argon2: the Contrarian is right on the cryptography. But a gap the peer review caught — nobody confirmed whether the PIN travels in plaintext before reaching the server-side hash. That analysis gap is itself a finding.

Blind Spots the Council Caught (via Peer Review)

The anon key is public and unguarded. The Supabase anon key lives in the deployed config.js, is visible to anyone who views source, and is the actual Authorization header for unauthenticated callEdge calls. Anyone can enumerate all customer phone numbers, stamp counts, and loyalty data right now. This is more immediately exploitable than the XSS.

The QR code is static and never expires. It encodes a customer ID and has no rotation or invalidation mechanism. A screenshot shared between customers allows indefinite impersonation to accumulate stamps. For a loyalty system, this is the primary abuse vector — and the app currently does nothing about it.

The stamp cooldown is client-side only. The lastStampTime check in staff.js is browser-only. Any request to the Edge Function bypassing the UI bypasses the rate limit entirely. The server does not enforce cooldown.

GDPR and privacy compliance is absent. The app collects phone numbers, birthdays, and behavioral loyalty data with no privacy policy, no data retention disclosure, and no consent mechanism. A regulatory complaint requires only one informed customer.

The Recommendation

This is a 70% app. The last 30% is where it crosses from "impressive demo" to "elite production system." That 30% is not polish — it is the difference between a product that is trustworthy and one that is not.

The architecture is sound. Supabase, GitHub Pages, Vanilla JS, GitHub Actions — defensible stack for this use case. The retro aesthetic is a real differentiator. The leaderboard mechanic is genuinely clever. The PWA approach eliminates install friction. These are real strengths.

The security posture has two critical issues open right now: the public customer data enumeration via the exposed anon key, and the XSS on e.note. Both can be weaponized today, by someone with minimal technical skill, using only a browser.

Fix these, address the QR impersonation design, lift the accessibility floor, and add a privacy policy. Then it earns "elite."

💬 Advisor Responses
The Contrarian This app has bones. It is not production-ready.

The 9,000-ID space is a timebomb. At a real café with any regularity, collisions become statistically likely well before you hit capacity — and there's no collision detection, so two customers silently share a QR code. One person redeems another's reward. Nobody notices until a customer is furious.

The e.note innerHTML injection is an XSS vector, full stop. Staff or admins can enter crafted input that executes in any browser viewing that history. On a shared staff device, that's a session hijack waiting to happen.

SHA-256 is not a password hashing algorithm. It's a checksum. PINs hashed with SHA-256 plus salt are crackable in seconds with a GPU and a wordlist. bcrypt or Argon2 exist for exactly this reason.

The font sizes are not an aesthetic choice — 5px–8px text is inaccessible under WCAG 2.1 AA, period. Combined with user-scalable=no, you've actively blocked the compensatory mechanism users with low vision rely on. This is legal exposure for a public-facing commercial product.

CDN dependencies without SRI mean a compromised CDN silently injects malicious code into your auth flow. Dead code in config.js signals an abandoned auth migration with inconsistent security assumptions baked in. The service worker path mismatch means offline functionality will silently fail on the custom domain.

The First Principles Thinker Technical sophistication ≠ production-ready.

What problem are you actually solving? A small café wants to reward repeat customers. The success metric: do loyal customers feel recognized, and do they come back more often? Everything else is downstream of that.

"Production-ready" for this context means: don't break during a Saturday morning rush, don't embarrass the owner in front of a customer, don't create legal or financial liability. That's the bar.

High impact: The 9,000-ID space with no collision detection is a genuine operational failure. Two customers sharing a QR code = stamps going to the wrong account = a trust-destroying moment at the counter.
High impact: innerHTML injection of e.note. The threat actor is more likely a disgruntled employee than an external hacker — which makes it more probable, not less.
Medium impact: 5px–8px fonts + zoom locked = functional barrier for core users.
Low actual impact at this scale: JWT sessionStorage, client-side birthday logic, missing SRI.

The deeper wrong assumption: treating "technically sophisticated" as a proxy for "production-ready." The unsophisticated failure — a customer can't read the screen — will hurt the business far more than a missing SRI hash.

The Expansionist This developer built something businesses would pay for.

This is a full-stack loyalty platform disguised as a café app. The real asset isn't the stamp card — it's the customer behavior graph. Visit history, birthday data, leaderboard mechanics, redemption patterns: this is exactly what small businesses pay $200+/month for through Toast, Square Loyalty, or Paytronix.

The opportunity hiding in plain sight: white-label SaaS. The tech stack is intentionally portable — vanilla JS, Supabase, no proprietary lock-in. The retro aesthetic is a differentiator. PWA means zero install barrier. The leaderboard is the most exciting feature — weekly top 5 on Instagram = word-of-mouth engine.

Left on the table: push notifications, geo-triggered visit detection, referral stamping, seasonal campaigns.

Note: Peer reviewers unanimously flagged this response as the session's biggest blind spot — dismissing ID collision and font legibility as "polish problems" could lead to shipping a system with genuine data integrity failures.

The Outsider Built to be admired by developers. Not yet built for the person who wants their tenth coffee free.

The first thing a café regular sees is text they literally cannot read. 5–8px font is not a design choice — it is a barrier. And they cannot zoom in to compensate because user-scalable=no removes that escape hatch entirely.

A 60-year-old retiree picking up their morning coffee does not know they are a "PLAYER" with "HP." The gaming metaphors are internally consistent but assume the user is in on the joke. Regular café customers are not in on the joke. They will feel confused, then embarrassed, then done.

The brackets around buttons — [ SIGN IN ] — look broken on first glance. Not stylized. Broken. The confirm() dialog for account deletion is a browser-native popup that looks like a system alert on mobile — alarming and unpolished. "NOOK-XXXX" displayed prominently as the primary identity marker means nothing to the customer.

Cohesion is not the same as usability.

Peer Reviews 4 things the advisors collectively missed — surfaced in review

1. Anon key data exposure (caught by Reviewers 1 & 2)
The Supabase anon key is in the deployed config.js, visible in page source, and used as the Authorization bearer token for all unauthenticated Edge Function calls. Anyone with the URL can enumerate all customer records — phone numbers, stamp counts, birthday data — with a single fetch. This is the highest-priority issue in the entire codebase.

2. Static QR code enables impersonation (caught by Reviewer 5)
The QR encodes the customer ID and never rotates or expires. A customer who photographs another's card can impersonate them indefinitely to accumulate stamps. For a loyalty system, this is the primary abuse vector — and the current design has no defense against it.

3. Stamp cooldown is client-side only (caught by Reviewer 1)
lastStampTime in staff.js is a browser check only. A direct API call to the Edge Function bypasses the rate limit entirely. The server must enforce cooldown, not the browser.

4. Privacy compliance is absent (caught by Reviewer 3)
The app collects phone numbers, birthdays, and behavioral loyalty data with no privacy policy, no data retention disclosure, and no consent mechanism. A regulatory complaint does not care how charming the pixel aesthetic is.
